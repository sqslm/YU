## 1. 已确认问题与最小复现

### R0：基准的用户环境隔离不完整（先处理，再运行基准）

`scripts/benchmark-electron-app.mjs` 的 `readRunKey()` 会列举名称含 `typeless|electron` 的启动项，以 `split('=').slice(0,2)` 解析；`restoreRunKey()` 将本次前后新增的匹配项都当成自有项删除，并复写原匹配项。因此另一个 Electron 程序在采样期间新增启动项，也会被误删；原值包含等号时还会被截断后写回。

外部复核通过执行这两个生产函数、替换 `spawnSync` 为记录命令的替身确认：`OtherElectronApp=C:/fake.exe --flag=a=b` 被读成 `C:/fake.exe --flag`，且会产生删除 `OtherElectronApp` 的命令。没有写真实注册表。

- [ ] 先消除这种按名称/前后差集推定所有权的恢复逻辑。首选让自有测试进程在两侧相同的诊断启动封装下不调用 `app.setLoginItemSettings`；保留正常产品行为，并记录封装及其哈希。仅设置独立 `--user-data-dir` 不足以隔离该系统级设置。
- [ ] 不批量备份/恢复用户的 Run 键，不删除其他程序项，不用“名称含 electron”判定本轮所有权。若确实需要解析注册表结果，使用结构化结果或只在第一个等号切分，保留完整类型和值；本轮不要用真实用户项做破坏性故障注入。
- [ ] 以替身覆盖：其他匹配名的项、值含多个 `=`、测试期间用户自行改变原值。验收是没有针对这些非自有数据的写入/删除命令，失败收尾同样如此。隔离做不到时先报告，不继续跑会污染环境的全量基准。

### R1：新建或回收后重建 Pill，首条播放命令会丢失

当前 `NoteAudioPlayer.control()` 和 `createSpeechPlayback()` 在取得 `barSink()` 新建的窗口后立刻 `webContents.send()`。真实播放监听器要等 `src/renderer/src/bar/Bar.tsx` 的 React effect 注册；`bar:ready` 目前只重放 pipeline 状态与设备请求，不重放播放命令。

外部隔离复现使用真实构建的 `bar.html`、preload、`NoteAudioPlayer` 和 IPC 信任校验，并拒绝麦克风权限：创建并加载窗口后立即 `control('status')` → **“录音播放没有响应”**；同一窗口发出 `bar:ready` 后再次查询 → `idle`。诊断脚本及结果保留在 `E:/code/deepseek-harness/work/stage18-review-20261104/real-bar-probe.ts`、`real-bar-probe.cjs`、`real-bar-result.json`，仅作已有复现参考；不要未经检查执行会写出文件的旧探针。简单 DOMContentLoaded 替身页面反而通过，所以不能只用该替身宣称真实页面已就绪。

- [ ] 在实际使用播放服务前等待同一个窗口的真实 `bar:ready`，再发送当前仍有效的命令。复用一个必要的就绪机制，不为每条命令添加固定 sleep 或单独轮询。`did-finish-load`、DOMContentLoaded、BrowserWindow 对象存在均不等于 React 播放监听器已安装。
- [ ] 同步审查随记播放和云 TTS 的实际入口；新的窗口消费者不能继续假定 Pill 永远存活。只读状态、回执校验与“确保创建窗口”应区分，不能为了验证迟到/伪造回执而新建窗口。
- [ ] 保持合理的现有启动/响应预算，处理等待期间取消、加载失败、窗口销毁/崩溃、旧窗口迟到 ready、旧请求被新播放替代；失败必须清理监听器、定时器和 pending，请求取消后不得迟到起播。不要扩大 8 s/20 s 预算来过测试。
- [ ] 添加有真实失效信号的回归：冷创建、回收后再创建、已就绪三类窗口；至少有真实构建的 bar/preload 冷路径用例。若无窗口时 `status` 合理返回 idle 而不创建，也必须另外验证真正的冷启动 play 路径，不能只靠 status 快捷返回绕开丢命令问题。

### R2：播放占用状态仍以推算时长释放，不能证明不会截断或永久常驻

已有 WIP 对暂停及未知时长选择保留 Pill，方向应保留；但已知时长仍以“剩余时长 / 速率 + 1.5 s”清除忙态。缓冲等待、实际播放进度与结束事件可能与墙钟不同。现有 renderer 播放器主要回复控制命令，不能假设已有连续状态或自然结束上报。

- [ ] 检查 `src/renderer/src/bar/noteAudio.ts`、`Bar.tsx`、`src/main/note-audio.ts`、WIP 跟踪器及 `wireBarRetirement()`。用当前播放 owner 的真实结束/错误/停止和必要的媒体状态变化释放占用，不仅靠估算时长就认定结束。
- [ ] 播放、缓冲及需要继续播放的暂停态不能在 30 s 回收下被截断；暂停后恢复必须保留同一录音、位置和速率。明确停止/结束、owner 销毁和退出时要释放忙态及 pending，不能由新窗口或其他请求的迟到回复覆盖当前 owner。
- [ ] 不把可恢复暂停自动变成停止来节省内存；如果仍需任何到期机制，应有可验证的实际进度依据，不能靠到期猜测已停止。不要为此建立通用播放器框架。

### R3：CPU 量纲与开窗延迟的计量不可用于当前采纳判定

外部执行现有 `readCpuMs()`、将 `GetProcessTimes` 替为确定的 FILETIME 输入后确认：user=10,000,000 个 100 ns tick，即 1000 ms，函数却返回 `userMs=1`。代码先除 10,000 得到毫秒，又除 1000，实际秒数被标成毫秒。

此外，`firstOpenLoop()` 的计时区间内，`waitForHub()` 每次先同步启动 PowerShell/WMI 列进程，再 EnumWindows，约 1 s 的查询开销混入开窗延迟。`coldRun().startupMs` 则包含固定等待 5 s、进程树/内存查询，还被加入 `firstOpen` 的 20 次开窗样本，形成 n=21 的混合口径。

- [ ] 修正 FILETIME→ms，仅做一次正确换算并保留适当精度。用已知 tick 值以及实际受控 CPU 任务对照验证单位；报告窗口时长与核数，不能只把旧 JSON 数字乘 1000 就宣称重测完成。
- [ ] CPU 必须说明对新生/退出进程的覆盖。优先复用已有 Windows job 记账方法；如果仅统计前后共同存活 PID，应标明局限并将缺失项列出，不得标为完整进程树或按 0 处理。
- [ ] 把 PowerShell/WMI 枚举移出延迟轮询的计时区间。可预先取得自有主进程 PID，再用薄的原生窗口查询观察；为计时源、开始/结束事件和采样分辨率留证据。
- [ ] 冷进程启动、冷 Pill ready/首次必要状态可呈现、首次打开主界面、再次打开主界面分开记录。不要把固定 sleep、内存采样完成或 `bar:ready` 分别冒充启动完成、开窗完成或视觉空白为零。
- [ ] 每类开窗至少 20 个有效样本，失败/超时单列并计入有效性判断，不挑掉最慢值过门槛；冷启动样本不混入开窗分位数。`compare-app-resources.mjs` 根据这些真实口径更新，必要条件缺失时拒绝自动 adopted。
